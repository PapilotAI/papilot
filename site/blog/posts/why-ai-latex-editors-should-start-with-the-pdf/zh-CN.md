在修改学术论文时，研究者的视线几乎总是停留在排版后的 PDF 页面上。你会对着版面通读证明，发现某个记号掩盖了前提假设，或是注意到某张图注没有把曲线的含义交代清楚。然而，一旦打算动手修改——无论是亲自改写还是借助 AI 助手——传统工具都会要求你离开成稿页面，回到 `.tex` 源码文件里去操作。

几十年来，在排版视图与原始 LaTeX 源码之间来回切换，一直被当成科学出版无法回避的代价。哪怕如今代码智能体已经能够跨文件编辑复杂项目，主流工具却依然沿用着已经落伍的交互方式：把最核心的工作空间留给源代码编辑器，而把排版后的手稿降格为旁侧的预览窗。

我们在设计 [Papilot](https://github.com/PapilotAI/papilot) 时做出了一个鲜明的判断：在 AI 辅助科学写作时代，以源码为中心的交互模式已经落伍了。作者推敲文意、读者评判论文，面对的都是排版后的页面，因此成稿本身才应该独占主工作区。Papilot 把核心空间完全交给 PDF，不在界面里给常驻源码编辑器留位置。底层磁盘上保存的依然是标准的本地 LaTeX 文件；如果作者确实想查看或手动修改源码，随时可以用自己顺手的外部编辑器直接打开本地项目文件。

## 为什么 Overleaf 和 Prism 的交互方式已经落伍

无论是经典的云端 LaTeX 编辑器，还是主打 AI 的新一代工具，之所以没有找到正确的交互方法，根源都在于它们依旧把主要空间让给了源代码。

根据 Overleaf 的[新版编辑器官方指南](https://docs.overleaf.com/getting-started/how-do-i-use-overleaf/redesigned-overleaf-editor)，其界面左侧为编辑窗格、右侧为 PDF 查看器，支持在代码模式与可视化模式之间切换、重新编译、调整或隐藏窗格，以及通过 SyncTeX 在源码与 PDF 之间跳转。即便可以折叠窗格或切换可视化编辑，它的编辑界面依然与最终排版页面分离，源码编辑仍然占据核心地位。

把更强的 AI 塞进这种传统源码编辑器里，并不能解决交互错位的问题。按照 OpenAI 的 [Prism 故障排除文档](https://help.openai.com/en/articles/20001050-troubleshooting-prism)，其编辑器内置助手会生成带有“保留/撤销”操作的 LaTeX 代码片段、标记行内源码错误、应用修改并重新编译，同时依赖独立的 PDF 预览窗格查看结果。（OpenAI 已在 [Prism 迁移至 Codex 的官方指南](https://help.openai.com/en/articles/20001615-prism-to-codex-migration-guide)中宣布 Prism 即将退役；本文讨论与批评的对象是它所采用的交互模式。）

无论 AI 是外挂在云端 IDE 旁，还是内嵌在源码编辑窗里，作者承受的交互负担并没有变：你依然要在“版面上的修改意图”与“编辑器里的 `.tex` 标记”之间来回充当翻译。你还得在代码窗格里和 AI 拉扯补丁、等待重编译，再把视线移到另一侧的预览区，去核对排版结果是不是自己想要的样子。

## 为什么源码 diff 是在让作者替编译器干活

不妨设想一个多文件论文项目里的常见修订场景。你在检查第 7 页的一条引理时，意识到某个估计量的指标集需要把观测样本与留出样本区分开来。要想干净地完成这次修改，你需要更新一处行间公式，调整上下文段落里的行内记号，并核对交叉引用的表注是否仍然一致。

在以源码为中心的工作流里，你得先在多个 `.tex` 文件间翻找对应的 `\begin{equation}` 或自定义宏，在编辑器里向助手提要求，然后面对一片红绿相间的源码 diff。为了判断修改是否准确，你不得不在脑海里充当一次 LaTeX 编译器：心算 `\mathcal`、`\hat`、多层上下标嵌套、间距微调以及宏展开。就算随后重新编译了项目，你依然要在预览窗的第 7 页上肉眼搜寻刚才改了哪里，凭记忆与修改前的版面做对比。

源码 diff 适合用来排查命令和语法细节，却无法直观呈现公式在行间的视觉节奏，也看不出图注与图表摆在一起是否清楚。让研究者透过零碎的 `.tex` 代码块去核实学术修改，等于强迫作者在做学者的判断之前，先替编译器做一遍解析工作。

## 把工作空间彻底还给排版手稿，不给无关面板留位置

当排版后的 PDF 真正成为操控界面时，改稿体验会发生根本变化。Papilot 不再把编译产物视为流水线末端被动的预览图，而是让排版页面成为每一次修订循环的起点与终点，并且不给源码面板留任何常驻空间。

![展示四阶段修订循环的示意图：作者在渲染后的 PDF 上批注，接入的 AI 智能体编辑底层 .tex 文件，Papilot 编译项目，随后作者在 PDF 上审阅排版后的修改前后对比并进入下一轮循环。](/assets/blog/pdf-first-workflow.zh-CN.svg "在 Papilot 中，作者始终停留在排版页面上提出需求并审阅修改，底层 .tex 源码的定位、编辑与编译则交给智能体和编译器完成。")

整个工作流在版面上直接构成闭环：

- **在页面上直接批注：** 直接在 PDF 上高亮句子，或框选公式、表格与插图，写下简短批注说明修改意图。
- **交由智能体修改源码：** 已接入的 AI 智能体会在本地项目中定位相关的 `.tex` 文件，并对底层 LaTeX 标记进行编辑。
- **后台自动编译：** Papilot 自动编译修改后的项目，生成最新的排版结果。
- **基于版面进行 PDF 审阅：** 无需阅读枯燥的源码 diff，你可以直接在页面上查看排版后的修改前后对比，决定接受、拒绝，或追加批注要求继续调整。

需要强调的是，不在软件里保留源码编辑窗格，绝不意味着抛弃 LaTeX，也不是对某个没有源码的任意 PDF 做逆向工程。Papilot 运行在你本机真实的 LaTeX 项目目录之上，磁盘上保存的依然是标准的 `.tex`、`.bib` 和样式文件。日常推敲和改稿时，你完全不必面对繁琐的源码标记；如果实在想看或亲自改动底层代码，直接用任何外部编辑器打开这些本地文件即可。

## 更直观的审阅视图，不能替代学者的专业把关

在版面上看得清楚，不代表学术内容就天然正确。AI 智能体可以把一处记号变更同步到三个章节，或是把一段冗长的证明草稿改写得紧凑流畅，但在这个过程中，它也可能悄然弱化某个定理条件、漏掉边界情形，或是曲解图表所展示的实验结论。

降低 PDF 审阅的阻力，是为了让作者的学术把关更专注，而不是放松警惕。当你不再需要分心去核对花括号是否配对、表格列对齐符是否错位，也不必在分屏之间靠 SyncTeX 来回定位时，就能把全部精力放回真正关键的问题上：定理推导是否依然严密？记号约定是否毫无歧义？正文表述是否经得起同行推敲？AI 给出的每一处建议都必须经过严格的学术核查，作者始终对论文中的论点、公式与图表负全部责任。

## 本地文件、Git 历史与自选智能体

一篇学术论文的打磨往往历时数月，涉及习惯各异的合作者，也依赖于个人或团队既有的工具链。由于 Papilot 直接读写本地纯文本文件，你的项目能够自然融入标准的 Git 工作流、外部代码编辑器与多人协作方式。在界面中审阅排版修改与管理版本历史是两个明确分离的环节：接受一条建议只会记录审阅决定；把审阅后的改动应用到稿件、执行 Git 提交（commit）或推送到远端仓库，始终是由你主动发起的独立操作。

同样的原则也适用于底层模型与运行环境。在 macOS、Linux 或 Windows 上使用桌面端时，你只需准备好本地 TeX 发行版（如 TeX Live 或 MacTeX）、Git，以及你平时惯用的 AI 智能体——无论是 Claude、Codex、Cursor、Copilot，还是 DeepSeek、Kimi、Qwen 等支持的 CLI 登录或 API 密钥。Papilot 本身采用 MIT 开源协议免费发布，模型调用直接通过你所选服务商的账户完成。
